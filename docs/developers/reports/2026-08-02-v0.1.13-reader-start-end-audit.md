# v0.1.13 reader `start`/`end` audit — issue #611, Lanes H and N

Date: 2026-08-02
Base: `eb62c6a056a7a8992fe1f00e115d6173050c64fc`
Status: **completed** (verified: `conda run -n gwexpy python -m pytest tests/io/ tests/timeseries/ -q`)

## The defect

GWpy's I/O registry lets any reader accept `start` and `end` through
`**kwargs`. Several GWexpy readers accepted them, discarded them, and returned
the whole file. The caller asked for a window and got everything, with nothing
in the returned object to say the request had been dropped — so a PSD over "the
quiet minute" or a coincidence search over one segment silently computes a
correct-looking number from the wrong samples.

The contract this audit enforces is that every reader does one of exactly two
things, and never a third:

* **applies** the window — the result equals `full_read.crop(start, end)`;
* **rejects** it — raises `IoNotImplementedError` before doing any work.

"Accepts and ignores" is the defect, and "warns and returns everything" is not
an acceptable substitute: warnings are routinely filtered, and the wrong array
still reaches the caller.

## Method

Every row below was **executed**, not inferred from reading the source. Each
family got a fixture, a full read, and a bounded read, compared against the
oracle `full_read.crop(start, end)`. Fixtures are 10 samples at 10 Hz spanning
`[0.0, 1.0)`, read with bounds `(0.2, 0.5)`, for which the oracle is 3 samples.

This matters because the first pass of this audit classified rows from source
reading alone and got three of them wrong (see the appendix).

## Why almost everything applies, and two things do not

The first pass of this fix cropped only NetCDF4, Zarr and generic HDF5 and made
the other nine backends refuse, on the reasoning that implementing the window
for each was a scope expansion unsuitable for a patch release. Review falsified
the premise, and the measurement that did it is worth recording:

**GWpy's own `wav` and `ascii` readers already implement `start`/`end`, by
cropping.** Measured: `gwpy.timeseries.io.wav.read(path, start=0.2, end=0.5)`
on a 1000-sample file returns 300 samples spanning `[0.2, 0.5)`. GWexpy
*shadows* the `wav` format in the shared registry, so making it refuse would
have meant GWexpy returning an error where the library it extends returns
correct data — a plain compatibility regression, and a worse outcome than the
bug being fixed.

That generalises. Every one of these readers already loads the whole source into
a `TimeSeriesDict` before returning it, so cropping is the same two lines
everywhere; "we cannot implement it" was never true. Refusing also *removes* an
argument callers may already pass, which is a larger behavioural change than
making that argument work.

So the rule is now: **apply the window wherever the result can be verified.**
Two backends cannot be verified — `ats.mth5` needs an mth5-conformant filename
and `xml.diaggui` a real DiagGUI product file, and the repository has neither —
so they refuse rather than ship an unexercised code path. That is the honest
answer to "we cannot show this works"; silently returning the full span is not.

A consequence worth noting: the earlier plan recorded `gbd` and `sdb` as
deliberate breaking changes, because their docstrings advertised `start`/`end`
as "accepted and ignored". With those two now cropping instead of raising,
**that breaking change no longer exists** — the documented wording becomes
wrong, not the behaviour.

## Where the HDF5 dict defect actually was

Worth recording because the first pass looked in the wrong file. gwpy's
`read_hdf5_dict` **does** forward `**kwargs` to `read_hdf5_timeseries`, and
calling the registered reader directly crops correctly. The loss happened in
GWexpy's own override, `gwexpy/timeseries/collections.py`
`TimeSeriesDict.read`: its `fmt in ("hdf5", "h5", "hdf")` branch reopens the
file with `h5py` and re-reads each dataset via
`TimeSeries.read(h5f, format="hdf5", path=...)` without passing the bounds
along. So `TimeSeries.read` and `TimeSeriesDict.read` disagreed about the same
file — the single-series path was right the whole time.

`gwexpy/timeseries/io/hdf5.py`, which the plan originally named as the fix
site, is a 45-line re-export shim of gwpy's module and contains no defect.

The same override has a `direct_readers` branch that dispatches `mseed`, `win`,
`ats`, `gbd`, `tdms` and `xml.diaggui` straight to reader functions, bypassing
the registry. That is why the fail-closed guard lives in the reader functions
rather than in `register_timeseries_format`: a registration-layer gate would
never see those calls.

## The clamp, and why cropping alone was not enough

`gwpy.types.series.Series.crop` computes its stop index as
`floor((end - x0) / dx)` with **no guard for `end < x0`**. The resulting
negative index is then interpreted from the end of the array, so a window that
falls entirely *before* the data returns a non-empty slice taken from the wrong
place. Measured: a series spanning `[10, 20)` cropped to `(0.2, 0.5)` returns
five samples covering `[10.0, 10.5)`, accompanied only by a `UserWarning` that
describes the opposite problem.

This is reachable through the fix, not around it: Zarr stores `t0` per array and
generic HDF5 per dataset, so one file can hold channels with different epochs
and a single bounded read can cover one channel and miss another. Cropping
naively would have re-created, inside the fix, the exact defect #611 is about —
plausible-looking samples from the wrong part of the file.

`apply_time_selection` therefore treats each series' own span as the limit of
the request. The first shipped form did this by clamping the bound *values* —
`max(start, span[0])` / `min(end, span[1])`, the same arithmetic
`gwpy.timeseries.io.hdf5.read_hdf5_timeseries` uses — and the second review
round showed that passing those synthesised values into GWexpy's `crop`
wrapper, which round-trips every bound through `to_gps` (integer nanoseconds),
silently dropped the final sample of any start-only read whose span edge is
not nanosecond-representable (measured: 47 samples where the oracle holds 48,
for hdf5, zarr, csv and wav alike at `dt = 1/30`), and re-created the negative
index at a non-ns `t0` (measured: nine samples for a window entirely before
the data). The current form never synthesises a bound: a side the caller did
not give, or gave outside the span, is forwarded to `crop` as `None`, and a
window that misses the data entirely is answered with a directly-sliced empty
series without calling `crop` at all. In-range bounds reach `crop`
bit-identical to the oracle's, so `result == full_read.crop(start, end)` holds
exactly. Pinned by `TestChannelsThatDoNotCoverTheWindow` and
`TestNonNanosecondGrids`.

## Intentional behaviour changes

* **Out-of-range windows now behave differently, and not uniformly.** Cropping
  correctly makes a gwpy safety net reachable for the first time: its registry
  defaults to `gap="raise"` when bounds are given without `pad`, and checks
  afterwards that the result covers the request. While readers returned whole
  files that check could never fire. It now fires for `nc` and `hdf.ndscope`,
  which reach the registry, but not for `zarr` or generic `hdf5`, which are
  served by early-return branches in `TimeSeriesDict.read` and instead return
  the empty crop. Those two also do not honour `pad`/`gap`. This divergence is
  pinned by tests rather than fixed: an empty result is visibly empty, unlike a
  full-span result masquerading as a windowed one, so it is a consistency wart
  and not the #611 defect. Unifying it belongs with the v0.2.0 reader-contract
  work.
* **Headerless CSV now reconstructs `dt` from the endpoints, not the median
  diff, when the time column is uniform.** Each diff of a decimal-written time
  column carries ~1 ulp of parse noise, and that noise was enough to make
  `crop`'s `floor((t - t0)/dt)` land one sample early — which gwpy 4's
  registry coverage check escalated to a `ValueError` on a fully in-span
  bounded read that gwpy's own ascii reader satisfies without complaint
  (found by the compatibility review). The end-to-end average spreads the same
  noise over N−1 samples; the median remains the estimator whenever the two
  disagree, so gappy or irregular columns behave as before. This also removes
  the one-sample offset the bypass single-series path had against gwpy for the
  same files.

## Out of scope, found along the way

* **Backend push-down.** NetCDF4 and Zarr read whole and crop. Asking xarray or
  zarr to read only the requested slice would be faster but is a performance
  change, and v0.1.13 is a bug-fix release. Reading whole is slower and correct.
* **`read_timeseries_zarr` returns a non-deterministic channel.** Zarr's
  `open_group().keys()` is not order-stable, so "read a Zarr store and return
  the first channel" returns a *different channel* on repeated reads of the same
  store, and `read_timeseriesdict_zarr` returns keys in varying order. Measured
  identical on the base tree, so it is pre-existing and not introduced here, but
  it is a data-correctness bug of the same family as #611 and deserves its own
  issue.
* **`crop` perturbs `dt` by one ulp — but only on some paths.** An earlier
  draft of this report claimed it happens "anywhere"; the physics review
  re-measured and found a regular `TimeSeries` keeps `dt` bit-identical
  through `crop`. The perturbation (`0.1` → `0.10000000000000003`) appears
  when `crop` re-derives `dx` from a materialised `xindex`, and in
  `TimeSeriesMatrix.crop`. Measured on the base tree, so pre-existing, but on
  those paths it breaks the project's `assert result.dt == input.dt` metadata
  rule and any `df = 1/(N*dt)` bit-comparison.
* **`TimeSeriesDict.crop` drops `_gwexpy_io` provenance.** Measured on the base
  tree. `apply_time_selection` carries it across explicitly so that a bounded
  read does not lose metadata an unbounded read keeps, but the underlying
  `crop` still loses it for direct callers.
* **NetCDF4 round-trips `t0` and `dt` lossily.** The writer quantises `dt` to
  integer nanoseconds (`np.timedelta64(int(round(dt*1e9)), "ns")`), so
  1/16384 s becomes 61035 ns — a −2.6e−6 relative error that accumulates to
  ~172 samples of offset over 4096 s. A separate `t0` defect shifts GPS 10.0 to
  9.0 on write/read. Both are writer-side and pre-existing, but now they decide
  *which samples a windowed read returns*, not just the reported axis.
* **Reject messages name the canonical format, not the alias the user typed.**
  `format="miniseed"` reports `'mseed'`, `sqlite3` reports `'sdb'`, `dttxml`
  reports `'xml.diaggui'`. Cosmetic; affects only the two refusing backends now.
* **`format="ats.mth5"` via `TimeSeriesDict.read` never reaches the mth5
  reader.** `collections.py`'s `direct_readers` maps it to
  `read_timeseriesdict_ats`, the native header parser. Pre-existing routing bug,
  unrelated to selectors but found while tracing them.
* **ObsPy push-down.** ObsPy's `read()` natively accepts `starttime`/`endtime`,
  so seismic formats could avoid loading whole files rather than cropping after.
  A performance change, deferred with the other push-downs.

## Appendix — corrections to the first pass of this audit

The first pass concluded **BLOCKED** and did not execute the optional backends.
Its findings are retained here rather than deleted, per the project's
planning-document rule on keeping error traces.

1. **"Optional NetCDF4/Zarr dependencies are absent" — wrong.** All of
   `h5py 3.16.0`, `xarray 2026.2.0`, `netCDF4 1.7.4`, `zarr 3.1.5` and
   `scipy 1.12.0` are installed in the `gwexpy` environment. The observed
   `2 skipped, exit 5` was caused, on the Zarr side, by the environment gate
   `GWEXPY_ALLOW_ZARR=1` — not by a missing package. `tests/io/test_netcdf4_reader.py`
   passes 17 tests on its own. The BLOCKED verdict rested largely on this.
2. **Generic GWpy HDF5 classified as "Applied by owner" — wrong for the dict
   path.** Measured: 10 samples returned where the oracle is 3. The row was
   derived from gwpy's source without executing GWexpy's override, which is
   where the bounds were being dropped.
3. **Seismic classified as "delegated to ObsPy; unsupported selectors are
   expected to error" — wrong.** Measured: 100 samples returned where the oracle
   is 25. ObsPy silently ignores the unrecognised keywords. Because of this
   misclassification, seismic was initially left out of the fail-closed list; it
   was added after measurement.

The common cause of all three is the same: classifying a reader by reading it
instead of running it.

## Appendix — corrections from independent review of the fix itself

Two read-only reviewers went over the implementation. Each finding below was
re-measured before being acted on; all of them changed the shipped code.

1. **The fail-closed design was wrong for most backends.** Measured: gwpy's own
   `wav` and `ascii` readers crop. Refusing would have regressed against the
   library GWexpy extends. Nine backends moved from refuse to apply; the
   `gbd`/`sdb` breaking change disappeared with them.
2. **Cropping alone re-introduced silent corruption.** Measured: a channel
   spanning `[10, 20)` cropped to `(0.2, 0.5)` returned five samples from
   `[10.0, 10.5)`. Fixed by clamping to each series' own span before cropping.
3. **Two silent-ignore holes remained after the format readers were fixed** —
   the directory-of-CSV collection reader and `TimeSeriesList.read`, both of
   which re-read entries themselves without forwarding the bounds. `TimeSeriesList`
   is the direct sibling of the `TimeSeriesDict` HDF5 branch and was missed
   because the first test file never exercised the list type at all.
4. **Provenance was dropped exactly when a window was requested** — worse, in
   that one narrow respect, than the bug being fixed, which at least returned
   the metadata along with the wrong samples.

Both reviewers also reported the worktree changing underneath them mid-review,
with one run showing many failures that did not reproduce. That was this
session editing the same worktree while the reviews ran, not a third party; the
lesson is to snapshot a tree before handing it to a reviewer, and it is recorded
here so the observation is not later mistaken for evidence of instability in the
change.

## Appendix — second review round, against the frozen commit

After the first fix was committed, three read-only reviewers (physics,
Python quality, gwpy compatibility) went over the *committed* tree — this time
with nothing editing it underneath them. Every finding below was independently
re-measured in this session before being acted on; all of them changed the
shipped code again.

1. **CRITICAL (physics): the clamp itself silently dropped the final sample.**
   The clamped upper bound was a float synthesised from the series' span, and
   GWexpy's `crop` wrapper quantises every bound to integer nanoseconds via
   `to_gps`. A span edge like `64/30` s rounds *down*, so a start-only read
   returned 47 samples where `full_read.crop(start)` returns 48 — measured
   end-to-end for hdf5, zarr, csv and wav. The `dt=0.1` test fixture rounded
   harmlessly upward, which is why the first test round passed. The same
   mechanism re-created the negative-index wrap at a non-ns `t0` (nine samples
   for a window entirely before the data), and emitted a spurious
   "crop given end larger than current end" warning on reads that never gave
   an end. Fixed by never synthesising a bound: out-of-span or missing sides
   are forwarded as `None`, and empty intersections are built by direct
   slicing without touching `crop`.
2. **HIGH (python + physics, converging): the fast paths crashed on bound
   types gwpy documents.** The registry runs `to_gps` on `start`/`end` before
   readers see them, but `TimeSeriesDict.read`/`TimeSeriesList.read` bypass
   branches handed the raw values to `float()` — an `astropy` Quantity died
   with `TypeError`, a date string with `ValueError`, while the same input on
   the single-series registry path worked. Fixed by normalising once at the
   `apply_time_selection` choke point; numeric input passes through `float()`
   untouched so the bypass paths keep their (better) precision.
3. **HIGH (compatibility): a fully in-span bounded read of a headerless CSV
   raised `ValueError` where gwpy's own ascii reader succeeds.** The reader's
   `dt` was the median of the time-column diffs, each carrying ~1 ulp of
   decimal-parse noise — enough to make `crop` land one sample early and trip
   gwpy 4's registry coverage check. Fixed in the reader's `dt`
   reconstruction; see "Intentional behaviour changes".
4. **MEDIUM/LOW:** the `_gwexpy_io` provenance dict was carried by reference
   (now copied); a docstring named the wrong exception (`UnitConversionError`
   → measured `TypeError`); the mapping dispatch used `hasattr(data, "items")`
   (now `isinstance(data, MutableMapping)`); and this report's claim that
   `crop` perturbs `dt` "anywhere" was an over-generalisation (corrected in
   place above).

The compatibility review also verified, against `astropy`'s and gwpy 4.0.1's
registry source and by execution, that `IoNotImplementedError` propagates
cleanly — the registry has no path that swallows a reader's exception and
falls back to another reader — and that the `wav` reader now matches gwpy's
own bit-for-bit, including the out-of-span warning/pad behaviour.

Nineteen regression tests pin these findings
(`TestNonNanosecondGrids`, `TestBoundTypes`, `TestHeaderlessCsv`,
`TestProvenanceCopy`); ten of them fail against the first shipped fix.
