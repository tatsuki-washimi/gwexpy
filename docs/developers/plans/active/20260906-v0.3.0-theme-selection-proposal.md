> **Status:** Proposal / Directional only

## Decision requested

Select **Explicit Time and I/O Dispatch Semantics** as the next candidate release
objective, subject to review of this proposal and the issue acceptance criteria.
The selection would make time interpretation and reader dispatch explicit and
predictable across the supported formats and collection backends. It would not,
by itself, authorize implementation, create a milestone, or assign a version.

The current roadmap already records this theme as `Directional` under [I/O time
and dispatch semantics](../../../ROADMAP.md#io-time-and-dispatch-semantics). This
proposal makes the candidate objective, dependency order, acceptance evidence,
and migration rules reviewable before any scope is committed.

## Release objective

A user reading supported experiment data should receive a GWexpy object whose
absolute or relative time reference is explicit, documented, and reproducible.
The same collection operation should also have the same dispatch and `gap=` /
`pad=` behavior regardless of which supported backend serves it.

The release objective has two independently testable tracks:

- **Track A — explicit time interpretation:** timezone, numeric time scale, unit,
  epoch, and BWF profile semantics are declared by the format contract and fail
  closed when the input is ambiguous.
- **Track B — dispatch and reader behavior:** collection fallback registry choice
  is decided and recorded first; then `TimeSeriesDict.read` exposes consistent,
  documented `gap=` / `pad=` behavior across supported backends.

Both tracks must be green for the theme to be considered complete. A partial
Track A or Track B result is a documented deferral, not a completed theme.

## Required scope

### Track A — time interpretation contract

The required issues are [#632](https://github.com/tatsuki-washimi/gwexpy/issues/632),
[#634](https://github.com/tatsuki-washimi/gwexpy/issues/634), and
[#636](https://github.com/tatsuki-washimi/gwexpy/issues/636).

- **#632 — WIN/WIN32:** add a keyword-only timezone contract, accepting IANA
  names and numeric offsets. A missing timezone must fail before an absolute epoch
  is returned. Multi-file reads must forward one interpretation consistently and
  provenance must identify the supplied timezone and epoch source.
- **#634 — numeric CSV time:** represent time scale and unit explicitly in the
  format configuration and reader override. GPS, Unix, and relative values must
  have distinct conversions; relative values require an absolute epoch when an
  absolute `t0` is requested. No magnitude-based GPS/Unix inference is allowed,
  and calendar-component columns remain a separate timezone contract.
- **#636 — BWF:** keep ordinary WAV behavior unchanged. Parse BWF calendar fields
  and `TimeReference` only through an explicit opt-in or a distinct BWF format
  contract. A timezone is required unless a named profile supplies one; the
  computed epoch is converted to GPS exactly once and its source is recorded.

Track A must deliver one cross-format time-interpretation conformance matrix that
covers explicit success cases, missing-information failures, precision, precedence,
and provenance for all three issues.

### Track B — dispatch and reader semantics

The required issues are [#444](https://github.com/tatsuki-washimi/gwexpy/issues/444)
and [#616](https://github.com/tatsuki-washimi/gwexpy/issues/616), in that order.

- **#444 — collection registry decision:** decide whether
  `FrequencySeriesDict`, `FrequencySeriesList`, and `FrequencySeriesMatrix`
  collection fallback keeps `astropy.io.registry` or converges on
  `gwpy.io.registry.default_registry`. Record the decision, update reachability
  tests if required, and document any format reachability change.
- **#616 — gap/pad consistency:** after the registry contract is fixed, define and
  test one behavior for `TimeSeriesDict.read(..., gap=..., pad=...)` across zarr,
  generic HDF5, NetCDF, and `hdf.ndscope` routes. Either every supported route
  applies the same semantics or every unsupported combination is rejected with a
  clear, uniform error. No backend may silently return a differently interpreted
  result.

Track B must deliver both a collection dispatch/reachability matrix and a
cross-backend gap/pad matrix. The matrices must identify the backend, registry
route, accepted arguments, result semantics, and explicit failure behavior.

## Non-goals and boundaries

The following are explicitly outside this proposal:

- [#688](https://github.com/tatsuki-washimi/gwexpy/issues/688), the exact rational
  GPS time-axis contract. It is an independent minor-scale effort and is not a
  prerequisite for this theme.
- New file formats, new on-disk encodings, or a new registry mechanism.
- Silent reinterpretation of existing files, numeric magnitude heuristics, or
  unrelated backend behavior changes.
- General scientific algorithm changes, data-model redesign, or new public APIs
  unrelated to the stated time/dispatch contracts.
- GWexpy Studio, Docs Web redesign, CLI work, and other consumer-layer changes.
- A second broad GWpy compatibility audit; the v0.2.3 audit and its historical
  evidence remain closed and source-bound.
- Changes to the published v0.2.3 tag, artifacts, DOI, release records, or
  historical review and qualification evidence.
- A commitment to v0.2.4, v0.3.0, a date, or a release order before the theme is
  reviewed and promoted to `Committed`.

If implementation uncovers a new runtime or scientific correctness defect outside
these boundaries, record it in a focused Issue and keep it out of the theme until
its own scope and acceptance criteria are reviewed.

## Issue dependencies and execution order

1. Freeze the API and migration decisions for Track A, including the distinction
   between civil timezone, numeric scale/unit, and BWF profile semantics.
2. The #632, #634, and #636 implementation and format fixtures may proceed in
   parallel once their contracts are compatible. Their results must feed the
   shared Track A matrix rather than three unrelated ad hoc tests.
3. Decide #444 before changing #616. The chosen registry is part of the #616
   backend matrix and its documentation; a later registry switch would invalidate
   the dispatch evidence.
4. Implement or explicitly reject #616 backend combinations using the same
   `gap=` / `pad=` vocabulary and error contract.
5. Review both matrices, English/Japanese documentation, provenance behavior, and
   the compatibility impact together. Track completion requires both matrices to
   be green and no unresolved required acceptance case.

The tracks can be developed independently after their contracts are fixed, but
promotion to a committed release scope requires both tracks and their shared
review gates.

## Migration policy

- **Fail closed on ambiguity.** Missing timezone, numeric scale, required unit,
  relative epoch, or BWF profile must raise a clear error before returning an
  absolute time. The implementation must not guess from numeric magnitude or
  the host locale.
- **Preserve ordinary behavior where it is already unambiguous.** Ordinary WAV
  remains relative unless the caller supplies `epoch=`. Existing on-disk payloads
  are not rewritten solely to add this contract.
- **Use explicit opt-in for behavior that can change an epoch.** If a legacy path
  needs a compatibility escape hatch, it must be named, documented, emit a
  warning/deprecation notice, and have a removal or review window. Silent legacy
  GPS interpretation is not a new default.
- **Record interpretation provenance.** Store the selected timezone/profile,
  scale, unit, epoch source, and relevant format fields so a read can be audited.
- **Keep precedence observable.** Caller arguments, format configuration, profile
  defaults, and file metadata must have a documented precedence order. Conflicting
  declarations fail rather than choosing one silently.
- **Avoid broad breakage.** Existing supported calls remain valid when their
  semantics are already explicit. Calls that were ambiguous may become a
  deliberate breaking change with a migration note and a focused error message.
- **Do not alter registry semantics indirectly.** A #444 migration must list any
  newly reachable or unreachable formats and provide a migration note for callers.
  #616 must use the same policy on every backend.
- **Review before release.** Any public signature or default change requires
  API/compatibility review and human scientific/data-model approval before a
  release candidate is qualified.

## Governance and decision gates

This proposal remains a review document. Until maintainers explicitly approve the
objective and create a milestone:

- no v0.3.0 milestone or release issue is created;
- #632, #634, #636, #444, and #616 remain Directional candidates;
- #688 remains an independent non-goal;
- `ROADMAP.md` is not promoted from `Directional` to `Committed`;
- no implementation branch or qualification evidence may claim v0.3.0 scope.

If the theme is selected, the next governance commit should promote exactly this
objective to `Committed`, create one milestone, assign only the accepted issues,
and preserve the non-goals and acceptance matrices in the committed release
record. Qualification must then be run on the final source; evidence from v0.2.3
or from an earlier candidate cannot be reused.

If the theme is deferred, retain this document as a proposal and record the reason
without rewriting v0.2.3 historical evidence.

## Open decisions for review

1. Which registry is the compatibility authority for #444: the existing Astropy
   registry or GWpy's default registry?
2. What exact public keyword names and configuration shape best express #634's
   scale, unit, and relative epoch without conflating calendar timezone?
3. Should BWF be an explicit `use_bwf_time` profile on `format="wav"` or a
   distinct format name, and which profiles, if any, define a fixed timezone?
4. What compatibility warning and deprecation window is appropriate for callers
   relying on legacy implicit numeric GPS seconds?
5. Which provenance fields and serialization boundary are stable enough to include
   in the public contract while preserving existing payload compatibility?

These decisions must be resolved in the issue contracts and acceptance artifacts;
this proposal intentionally does not choose an implementation design.

## Relationship to v0.2.3 closure

The v0.2.3 release and its post-release closure are complete and immutable. Its
GWpy compatibility audit, qualification run, publication source, and historical
review evidence remain the authority for that release. This proposal only records
possible future work and does not reinterpret any v0.2.3 finding as a new approval
or as evidence for a future release.
