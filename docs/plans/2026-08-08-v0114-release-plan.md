公開APIは追加しません。既存APIの誤った成功を明示的失敗へ狭めます。

- CSV/SDB: numericと既存`time_component`経路の両方を検査。不正な本文行は行番号付き`ValueError`。新しいISO列パーサーは追加せず、ISO由来の独立oracleをcanonical instantへ変換して検証します。single-rowは指定rateを優先し、未指定時は既存1秒fallbackを維持します。
- WIN: ファイル全体のpacket cadenceは連続必須。各channelの先頭late-start／末尾early-endは許容し、channel-local `t0`を保持します。開始後の内部欠落・再出現、rate変化、重複・逆行・global gapは拒否します。
- Time: `datetime64[s/ms/us/ns]`のinstantを保持し、`from_gps()`は全経路でUTC-aware。DST ambiguous/nonexistentとPython datetimeで表現不能なleap secondは配列単位でfail-closedにします。
- mth5: `mth5.read_file(..., file_type="metronix")`を使用。Ex/Ey→mV/km、Hx/Hy/Hz→nTを独立fixtureで照合し、空データ・開始時刻・rate・unit欠落は拒否します。
- Release control: `scripts/ci/release_contracts.json`を新設し、v0.1.13/v0.1.14のplan、evidence schema/path、review lanes、S→R許可path、artifact prefixを一元管理します。既存workflow_dispatch入力は維持し、未知tagはfail-closedにします。

## テスト・リリースゲート

- Cadence: regular、許容内/外jitter、missing、duplicate、backward、large gap、single-row、0.5µs、巨大epoch、NaN/Inf/NaTをnumeric/component/SDBで検証します。toleranceは相対時刻へ正規化したrepresentation-aware値かつ`< dt/2`とします。
- WIN: codec width 0–4、符号境界、rate=1、12-bit最大rate、channel順変更、年境界、payload長、警告回数、waveform/rate/channel-local `t0`を検証します。
- Time: NumPy全分解能、scalar/vector/Astropy parity、UTC/Tokyo/fixed offset、New York DST二境界、GPS leap-second前後と表現不能点を検証します。
- mth5: 合成raw値とJSON metadataを唯一の正解とし、mth5自身の出力だけをoracleにしません。minimum 0.6.8とresolver-currentを別gateで記録します。
- Zarr: UbuntuのPython 3.11/3.12それぞれで2.18.7、3.1.5、3.1.6、resolver-currentの8セルを実行します。現時点のresolver-currentは3.2.1です。[Zarr release history](https://pypi.org/project/zarr/)

Zarrの判定は次に固定します。

1. 両Pythonで3.1.5だけが失敗し他セルがgreenなら、`zarr`/`all`両extrasへ`!=3.1.5`を追加します。
2. 3.1.5がclean環境で通りcanonical condaだけ失敗する場合、依存制約を変えずconda環境を再構築します。
3. 複数version、resolver-current、2.18.7が失敗する場合、広域pinで回避せず原因を修正します。未解決ならrelease blockです。
4. exclusion後はresolverが3.1.5を選ばないこと、明示指定がconstraintで拒否されること、残りの対応セルとcanonical condaがgreenであることを最終gateにします。

`R`ではRuff check/format、MyPy、full pytest、I/O conformance、mth5/Zarr optional gates、EN/JA両docs stack、GWpy compatibility、Actionlint、locked `build --no-isolation`、artifact/twine、Python 3.11/3.12 wheel/sdist fresh-install、version/module path/`register_all()` smokeをすべて通します。

## S・R・公開手順

- 全コード・文書・統制・日付・metadataを含む完全SHAを`S`とし、scientific/physics、release/security、completionの3レビューを実施します。
- Critical/High/Mediumは修正必須です。Lowも修正またはissue化と明示承認が必要です。修正後は新しい`S`で影響gate/reviewを再実施します。
- `R`は`S`へsanitized evidenceと許可済みplan checkbox遷移だけを加えたSHAです。`S..R`にコード・一般文書・metadata変更を許しません。
- exact-R gate失敗時は旧`R`を破棄し、新しい`S`・レビュー・`R`を作り直します。後追い証跡commitは禁止します。
- `main`は`R`、`maint/0.1`は祖先確認・ruleset readback・承認後のnon-force fast-forwardで同じ`R`へ更新します。別SHAしか生成できない場合やdirect FF禁止時はforce pushせず停止します。
- candidateはfull SHA `R`、`expected_tag=v0.1.14`、明示的v0.1.14 evidence pathで実行します。
- tag承認直前にUTC日付とCHANGELOG/release notes/CITATION/Zenodoを再照合します。日付が変わった場合は旧`R`を公開せず、LDoc→LREL→LRC→新S/R→candidateを全面再実行します。
- local/remote tag不在、tag/branch rulesets、PyPI environment、deployment policy、Trusted Publisherをreadbackします。承認時snapshotとの差異があれば再承認まで停止します。
- 承認後だけannotated tagを`R`へ作り、peeled SHA=`R`を確認してpushします。PyPI smoke後、別承認でGitHub Releaseを作成しZenodoをreadbackします。retagは禁止し、公開後失敗はyank判断とv0.1.15 hotfixへ移します。
- Action run ID、R SHA、artifact digest、attestation locator、retention期限を#653へ記録し、PyPI/GitHub Release上の永続digestと照合します。
